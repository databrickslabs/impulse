ADAS Perception Frameworks

A survey of existing standards and message formats for representing a vehicle's perception snapshot at time t_i — the structured "what the vehicle sees of its environment right now" object that ADAS sensors (camera, radar, lidar) and downstream fusion produce. The goal is to inform the future complex time series extension to Impulse: pick (or take inspiration from) an existing schema rather than design one from scratch.

This is a research note for the design phase. No Impulse code changes are proposed here.

Motivation​

Impulse today models a time series as a sequence of scalar samples — see SampleSeries, backed by the channels silver-layer table with (container_id, channel_id, tstart, tend, value: double). This shape is the right primitive for ECU/OBD-II signals (engine RPM, vehicle speed, intake temperature, …) but cannot represent an ADAS sensor's output, where each timestamp produces a structured snapshot of the environment: a list of detected objects with geometry, classification and motion, lane geometry, free-space polygons, traffic-sign and traffic-light states, sensor health, and so on.

To extend Impulse to ADAS data we need a complex time series abstraction — samples whose value is an object, not a double. Before designing that in-Impulse type and its Delta-friendly serialization, this document evaluates the existing automotive and AD-stack schemas that already define what a perception snapshot looks like.

Scope and non-goals​

In scope:

  • ASAM standards directly relevant to perception representation: OSI, OpenLABEL, OpenSCENARIO + OpenDRIVE.
  • Open AD-stack message formats: Autoware autoware_perception_msgs, Baidu Apollo perception protobufs, and ROS vision_msgs / sensor_msgs.

Out of scope (deferred to follow-on notes):

  • Dataset formats (nuScenes, Waymo Open Dataset, KITTI, Argoverse). Their schemas borrow heavily from the standards covered here; they're consumers, not the source of truth.
  • Container / wire formats (MCAP, ROS bag, MDF4, Parquet/Delta). These are about how records are recorded and shipped, not what shape a perception snapshot is in.
  • The full Impulse complex-time-series data type and the ComplexSeriesSolver API. Note: the per-tick storage encoding for the chosen schema (OSI) is decided in this note — see Storage approach — because the choice is inseparable from how each framework scores on columnar/big-data fit.

Evaluation criteria​

Each framework is assessed along four axes:

  1. ADAS modality coverage — does the schema represent camera detections, radar tracks, lidar object lists / point clouds, multi-sensor fusion output, lanes, road geometry, traffic signals?
  2. Columnar / big-data storage fit — how cleanly does it round-trip through Parquet / Delta? Nested structs are fine; the friction points are oneof / polymorphism, very deep nesting, and dense per-tick blobs (raw point clouds, images) which prefer side-table references.
  3. Adoption and tooling — who uses it (OEMs, AD companies, sim vendors), maturity, availability of Python SDKs.
  4. Extensibility and governance — can custom fields be added without forking? Is the spec governed by an open body or a single vendor?

Frameworks​

ASAM OSI (Open Simulation Interface)​

Purpose. A generic, protobuf-based interface for the environmental perception of automated driving functions in virtual scenarios. Originally driven by the simulation community (sensor models in SIL/HIL), but the SensorData message is explicitly modeled as the perceived environment of an ADAS function and is increasingly used for recorded perception output as well.

Schema model. Protocol Buffers (proto3). The top-level interfaces are GroundTruth, SensorView, SensorData, HostVehicleData, TrafficCommand, TrafficUpdate, MotionRequest, and StreamingUpdate. Each is a complete snapshot at a single timestamp — GroundTruth.timestamp and the analogous fields on the other messages.

SensorData (the per-tick perception snapshot, most relevant to Impulse) carries:

  • moving_object[] — tracked vehicles, pedestrians, cyclists with kinematics, classification, dimensions, covariance
  • stationary_object[] — non-moving obstacles
  • traffic_sign[], traffic_light[], road_marking[]
  • lane_boundary[] — detected lane geometry
  • occupant[] — in-cabin perception
  • sensor_view ref — link back to the raw SensorView input
  • feature_data — radar/lidar/camera-specific low-level feature lists

GroundTruth is structurally similar (without sensor-side uncertainty) and is useful for labeled / replay data.

Modalities. Camera detections, radar object lists, lidar object lists, fused output, lane geometry, signals, environmental conditions — all in the same top-level message. Raw point clouds / images are represented as FeatureData references rather than inlined pixel arrays, which keeps the schema lean.

Governance & license. ASAM e.V. working group; Mozilla Public License 2.0 on the GitHub repository. Latest release at time of writing: v3.8.0 ("Krisp Kobayashi"), May 2026, demonstrating active maintenance.

Tooling & SDKs. Protobuf-generated Python (and C++, C#, Java, …) bindings are first-class — the repo is 96% Python by GitHub's classification, with generated stubs and helper utilities. Wide simulator adoption (CARLA, esmini, VTD, Carmaker, etc.).

Columnar / big-data fit. Two routes exist and matter for Impulse:

  • Native flattening. Protobuf maps in principle to nested Spark/Parquet structs (each repeated message becomes an array<struct>), and Spark 3.4+ ships from_protobuf for lazy field projection. The friction is the density of optional fields (OSI is wide and optional-heavy) and deep nested repeats (polygons, covariance matrices), plus the cost of evolving the Delta schema every time OSI does.
  • Opaque-blob storage (chosen for Impulse, see Storage approach below). Each tick is the protobuf wire-format bytes in a Delta binary column, parsed in a Pandas UDF on workers. Schema-stable, version-flexible, and the exact pattern Impulse already uses for SampleSeries blobs — at the cost of no Delta-level predicate pushdown into the perception payload. Hoisted summary columns at ingest recover cheap filtering for the common cases.

Raw point clouds / images are kept out of the per-tick blob and referenced via OSI's FeatureData URI pattern regardless of which route is taken.

Extensibility. Custom fields can be added via reserved-tag extension messages without forking the standard. The spec recommends per-vendor extension messages rather than editing core proto definitions.

Mini-example (paraphrased). A SensorData message stamped timestamp = 1700000000.123s containing five moving_object entries (each with id, base.position, base.orientation, base.velocity, base.dimension, vehicle_classification.type, and a positive-definite base.position_covariance), two traffic_sign entries with type / value, and a lane_boundary list describing the local lane geometry.

ASAM OpenLABEL​

Purpose. A standardized annotation / labeling format for multi-sensor recordings — the schema you'd use to publish ground truth for a labeled dataset, or to author labels for active learning. Not a runtime message format.

Schema model. JSON with a JSON-Schema definition. Element types: objects, actions, events, contexts, relations, each optionally carrying *_data payloads (e.g. object_data with bounding boxes, polygons, cuboids, keypoints). A frames map indexes elements by frame number, giving the per-tick view; static metadata lives at the file root.

Modalities. 2D/3D bounding boxes (rotated supported), polygons, cuboids, keypoints, segmentation (instance / semantic), plus action and relation labels. Sensor-stream metadata is captured but the format is camera-frame / lidar-sweep oriented — multi-sensor synchronization is via shared frame ids.

Governance & license. ASAM e.V.; v1.0.0 released November 2021. No major revision since, which is both a stability signal and a maturity caveat.

Tooling & SDKs. Open-source Python library uai-openlabel provides typed models; the WebLabel multi-sensor labelling tool emits OpenLABEL natively. The nuScenes / KITTI ecosystems converge with OpenLABEL via converters rather than native emission.

Columnar / big-data fit. JSON-rooted with deeply nested polymorphic *_data payloads. Translating directly to Parquet is painful — variant types inside object_data (e.g. bbox vs cuboid vs poly2d) typically need to be projected to a flat row-per-annotation layout. Better suited as an interchange format on the way in than as the on-disk Delta schema.

Extensibility. Strong — the spec is explicit about taxonomy / ontology imports and accepts user-defined attributes on every element type.

Mini-example. A 30-second clip with frames[1240] containing objects['car_07'] whose object_data.cuboid records position + dimensions

  • orientation, plus an action "lane_change_right" linked via a relation to the same object.

ASAM OpenSCENARIO + OpenDRIVE​

Purpose. Context standards. OpenDRIVE (XML, .xodr) is the road network description — geometry of roads, lanes, junctions, signage positions. OpenSCENARIO (XML 1.x / DSL 2.0) describes the dynamic scenario — what traffic participants do, often referencing an OpenDRIVE map.

Why they're in scope but not the primary fit. These are not per-tick perception snapshots — they describe a scene over time as scripts / parameterized scenarios. They are relevant to Impulse only as: (a) the source of the map a perception snapshot lives on, and (b) the format in which test scenarios that produce ADAS recordings are written. The per-tick output of executing an OpenSCENARIO scenario is typically an OSI GroundTruth stream.

Governance & license. ASAM e.V., free of charge. Active development; OpenSCENARIO 2.0 introduces a domain-specific language for scenarios.

Implication for Impulse. Out-of-band reference data: store the OpenDRIVE map alongside a recording's container metadata (so spatial queries can resolve "object at lane X, station Y"), and treat OpenSCENARIO as scenario metadata, not as the per-tick payload.

Autoware autoware_perception_msgs​

Purpose. ROS 2 message definitions for the Autoware Foundation's open-source AD stack — the actual wire format that perception nodes (detector → tracker → predictor) publish.

Schema model. ROS 2 .msg IDL (compiles to C++/Python). The package ships 20 message types; the perception object lifecycle is captured in three families, each with a singular and array form:

  • DetectedObject(s) — per-frame detector output: existence_probability, classification[] (ObjectClassification with label + probability), Shape (BOUNDING_BOX / CYLINDER / POLYGON + dimensions), DetectedObjectKinematics (pose + twist with covariance, orientation availability flags).
  • TrackedObject(s) — adds object_id (UUID), full pose+twist+accel covariance, is_stationary.
  • PredictedObject(s) — adds kinematics.predicted_paths[] (sampled future trajectories with probability).

Plus TrafficSignal / TrafficLightGroup(Array) for traffic-light state groups.

Modalities. 3D object detection / tracking / prediction (the AD-stack "middle of the funnel"), traffic-light state. Lane geometry lives in sibling package autoware_map_msgs; raw sensor I/O in autoware_sensing_msgs / sensor_msgs. Free-space and occupancy grids likewise live in adjacent packages — perception is not one-stop here, it's spread across packages.

Governance & license. Autoware Foundation (open-source community); Apache-2.0; latest release v1.12.0 / v1.13.0 (Apr–May 2026) — actively maintained.

Tooling & SDKs. First-class ROS 2 ecosystem — Python (rclpy) and C++ clients, RViz / Foxglove / Lichtblick visualization plugins, ros2bag and MCAP recording.

Columnar / big-data fit. ROS 2 IDL is straightforward to map to a Spark schema (no oneof polymorphism in the perception messages — Shape uses a type discriminator plus the union of dimension fields). The bigger issue is that perception state is split across multiple topics — DetectedObjects, TrackedObjects, PredictedObjects, TrafficLightGroupArray, plus non-perception topics — so a "snapshot at t_i" requires a join / synchronize step over message streams. There is no single-message envelope analogous to OSI's SensorData.

Extensibility. Adding fields requires forking the message definition or introducing a parallel topic; the spec is governed by the Autoware Foundation process.

Mini-example. A DetectedObjects message at header.stamp = 12.345s with three entries: a CAR (classification probability 0.92, BOUNDING_BOX 4.5×1.8×1.6, pose + 6×6 covariance) and two PEDESTRIANs (CYLINDER shape).

Baidu Apollo perception protobufs​

Purpose. Wire format for Baidu's open-source Apollo AD stack — analogous to Autoware's role, but protobuf-based rather than ROS IDL.

Schema model. Protocol Buffers. The central message is PerceptionObstacles (modules/common_msgs/perception_msgs/perception_obstacle.proto):

  • header — timestamp, frame, sequence number
  • error_code
  • perception_obstacle[] — list of PerceptionObstacle (id, 3D position, theta heading, 3D velocity and acceleration, length/width/height, polygon_point[], type (UNKNOWN/PEDESTRIAN/BICYCLE/VEHICLE) + sub_type (CAR/VAN/TRUCK/BUS/CYCLIST/…), confidence, tracking_time, motion_type, sensor_measurements[], position/velocity/acceleration covariance matrices)
  • lane_marker — lane boundary info
  • cipv_info — closest-in-path vehicle id
  • perception_waste[] — debris

Traffic-light state is a separate TrafficLightDetection proto.

Modalities. Fused 3D obstacles (multi-sensor — Apollo's perception is explicitly designed for camera+lidar+radar fusion), per-obstacle sensor-attribution via sensor_measurements, lane markers, traffic-light state. Like Autoware, this is the fused output of perception — not raw point clouds.

Governance & license. Apache-2.0, maintained by Baidu / ApolloAuto. Last major release v9.0.0, December 2023 — slower release cadence than Autoware or OSI; check the master branch for current development.

Tooling & SDKs. Protobuf-generated Python / C++ clients; uses Apollo's custom Cyber RT runtime (Apollo replaced its ROS-based messaging with Cyber RT in v3.5).

Columnar / big-data fit. Comparable to OSI — protobuf, deep nested structs, repeated polygon points. Slightly better than Autoware for a single-tick snapshot because everything (obstacles + lane markers + CIPV) sits in one envelope. Same caveats around projection.

Extensibility. Reserved-field convention typical of protobuf; non-trivial because Apollo's messages are tightly coupled to its internal modules.

Mini-example. A PerceptionObstacles at header.timestamp_sec = 1700000000.123 with seven perception_obstacle entries, a lane_marker block giving the two adjacent lane lines as cubic polynomials, and cipv_info pointing to obstacle id 4.

ROS vision_msgs / sensor_msgs​

Purpose. Generic robotics building blocks — not an automotive perception schema but the lingua franca primitives that automotive ROS-based stacks build on.

Schema model. ROS 2 .msg IDL.

  • vision_msgs — Detection2D, Detection3D, Detection2DArray, Detection3DArray, BoundingBox2D, BoundingBox3D, ObjectHypothesis(WithPose), Classification, LabelInfo, VisionInfo. A Detection3D is header + bbox + results[] where results is a list of ObjectHypothesisWithPose (class id, score, pose with covariance) — multi-hypothesis is supported natively.
  • sensor_msgs — Image, CompressedImage, PointCloud2, LaserScan, CameraInfo, Imu, NavSatFix. PointCloud2 is a generic height×width×fields binary layout that can carry XYZ, XYZI, XYZRGB, etc.

Modalities. Detection primitives for any modality (camera 2D, lidar/radar 3D), raw sensor I/O. No lane / free-space / traffic-light primitives — these must be modeled in a higher-level package.

Governance & license. ROS Perception working group; Apache-2.0. vision_msgs latest release v4.2.0, May 2025. Long-stable, widely adopted across robotics.

Tooling & SDKs. Universal in the ROS ecosystem; RViz visualization plugins; trivial Python access via rclpy.

Columnar / big-data fit. Simple, narrow schemas — clean Parquet mapping. PointCloud2.data is a bytes blob, which round-trips fine but is opaque to columnar predicates; for query-heavy point-cloud workloads it's better to explode to per-point rows (a separate table).

Extensibility. Convention is to wrap (publish on a custom topic with a custom message type that references vision_msgs primitives), not to extend in place.

Mini-example. A Detection3DArray at header.stamp = 12.345s with four Detection3D entries; each carries a 3D bbox in the base_link frame and a single ObjectHypothesisWithPose(class_id="car", score=0.93, pose).

Recommendation​

Schema choice​

Adopt ASAM OSI as the primary reference schema for the per-tick perception snapshot in Impulse's complex-time-series extension. Rationale:

  1. Coverage and shape match the goal. OSI's SensorData (and the structurally identical GroundTruth) is exactly a per-timestamp environment snapshot — moving objects, stationary objects, lanes, signs, lights, occupants, environmental conditions in one envelope per t_i. Autoware and Apollo are close, but Autoware splits the snapshot across topics and Apollo's release cadence trails OSI/Autoware.
  2. Industry weight in the automotive segment. OSI is governed by ASAM (the standards body Impulse already aligns with on the recording / data- model side) and is the de-facto interface used by every major automotive simulator. Recording-tool support is growing fast.
  3. Protobuf composes cleanly with Impulse's existing blob pipeline. Each per-tick OSI message is stored as serialized protobuf bytes in a Delta binary column and deserialized on workers via Pandas UDF — see Storage approach. This is the same execution shape Impulse already uses for SampleSeries (pickle+lz4 blob + worker-side deserialize via BlobSolver), so a future ComplexSeriesSolver slots into the 6-stage pipeline without re-shaping it. The blob route also decouples the Delta schema from OSI's 3.x release cadence — adding/removing optional fields needs no table migration. Raw point clouds and images stay out of band via OSI's FeatureData URI references rather than inlined into the blob.
  4. Extension story is clean. Vendor-specific fields are added via extension messages without forking the standard.

Secondary references to keep in scope as the design progresses:

  • Autoware autoware_perception_msgs as a cross-check on the detection/tracking/prediction lifecycle (Impulse will likely want to model the tracking lineage of an object, which Autoware's three-tier Detected/Tracked/Predicted hierarchy captures more explicitly than OSI).
  • ROS vision_msgs as the primitive set when ingesting from ROS-based recordings — straightforward Detection3D[] → OSI moving_object[] mapping.
  • OpenLABEL only when the data carries human / auto-labeled ground truth for evaluation; do not use it as the runtime per-tick schema.
  • OpenDRIVE as the out-of-band map artifact attached to a container (analogous to today's container_tags).

Storage approach: protobuf blobs in a Delta binary column​

Store each OSI tick as the serialized protobuf wire-format bytes in a binary column on a Delta table, and parse with the generated OSI Python bindings inside a Pandas UDF on the workers. The row model is one row per tick on an OSI stream, e.g.:

ColumnTypeNotes
container_idlongRecording / drive identifier (same as today).
channel_idintOSI stream identifier (e.g. one virtual sensor).
tlongTick timestamp in microseconds.
osi_versionstringOSI release the blob was produced against (e.g. 3.8.0).
payloadbinarySensorData / GroundTruth serialized via SerializeToString().

Why this fits Impulse. It is the same execution pattern Impulse already uses for scalar time series:

  • SampleSeries is serialized to a binary blob (pickle + lz4) and deserialized on workers — the OSI tick is the structural analogue, just with protobuf as the wire format.
  • The solver pipeline (QuerySolver) already filters → fetches blobs → deserializes → operates; a ComplexSeriesSolver slots in without rethinking the 6-stage shape.
  • SeriesCache / BlobSolver give a precedent for "load opaque payload, materialize on demand."

Trade-offs to keep in view:

  • No predicate pushdown into the perception payload. Filters like "any pedestrian within 20 m of the ego at this tick" run inside the UDF after the blob has been read and parsed. Mitigate by hoisting a small set of cheap, hot fields to top-level columns at ingest (see "hoisted columns" below).
  • No column pruning inside the blob. A query that needs only moving_object[].velocity still pays the IO and parse cost for the full SensorData. Acceptable if reports typically touch many fields; revisit if workloads turn out to be narrow.
  • Per-row parse cost. At 10–60 Hz over hour-long recordings, blob count per recording is non-trivial; protobuf parsing in Python is fast but not free. Same order of magnitude as the existing SampleSeries lz4+pickle round-trip.
  • OSI version drift. OSI evolves on a 3.x cadence; record osi_version per row so the UDF can pick the right descriptor. Cross-version reads are natively supported by protobuf's wire-format compatibility rules for added fields.

Hoisted columns for cheap filtering. Compute a small set of derived columns at ingest and persist them as native Spark types alongside the blob — analogous to today's channel_metrics pre-computed stats. Candidates: num_moving_objects, num_stationary_objects, has_traffic_light, ego_speed_mps, tick_index. These enable Delta-level predicate pushdown without forcing the full blob to be parsed.

Alternative considered: Spark native protobuf (from_protobuf). Spark 3.4+ can lazily project fields out of a protobuf-bytes column using a compiled descriptor. It's worth a benchmark for read-heavy paths where reports touch only a handful of fields, but it doesn't replace the UDF route — TSAL operators over object lists need arbitrary Python and protobuf objects, not just SQL access to fields. Treat from_protobuf as an optimization for hot queries, not the primary access pattern.

Open questions for the next phase​

These need answers before the Impulse complex-time-series data type and its solver are designed:

  1. Storage layout — decided in outline, details open. Per-tick OSI protobuf in a binary column (see Storage approach above). Still open: (a) does this live as a new variant of the existing channels table (carrying a payload: binary alongside the current value: double), or as a separate complex_channels table? (b) which "hoisted" columns are worth the ingest cost, and where do they live — on channels itself or on a new channel_metrics-style sibling? (c) what is the exact set of generic tick-level columns (t only, or (tstart, tend) mirroring the RLE shape)?
  2. Bulky payloads. OSI carries point clouds, images and lidar sweeps as FeatureData references rather than inline bytes — good. Still open: where do the referenced payloads live (UC Volume URI, dedicated Delta blob table à la today's BlobSolver, external object store)? Also: does Impulse need to read these on query, or only surface URIs for downstream tools?
  3. Tracking lineage. Detected / tracked / predicted state for the same real-world object across t_i needs a stable object_id and a join strategy across ticks. Closer to Autoware's three-tier model than OSI's single SensorData envelope.
  4. Map context. How is the OpenDRIVE map attached to a recording — as a container-level artifact, or hoisted into queryable rows (lanes, junctions) for spatial joins?
  5. Query DSL. How does TSAL grow to express selectors over object lists (e.g. "max number of pedestrians within 20 m for ≥ 200 ms") without leaking Spark internals into report definitions?
  6. Schema versioning. OSI evolves (v3.x cadence is fast); the Impulse schema needs a versioning + migration story comparable to today's value_type column on channel_metrics.
