Impulse · Extensibility

Plug in your own solver & measurement-DB — from config, without forking

Impulse reads a governed silver layer and executes a TSAL query over it through two replaceable seams. This guide shows how a customer supplies their own implementation of either, selects it by name in the report config (never a class path imported from config data), and keeps every existing config working unchanged.

Two seams, two concerns

MeasurementDB is where and how the silver data is read; QuerySolver is how a TSAL query is planned and executed over it. They are reached for different reasons — one is about getting the data, the other about what the engine does with it.

AbstractMeasurementDB

The read seam

Knows where the silver tables live and how to read them; returns raw Spark DataFrames. Knows nothing about query semantics. Customize it to:

  • Combine multiple physical tables into one logical table (join / union before Impulse sees it).
  • Read a non-Delta / non-UC backend — JDBC, REST, files on a path, a KV store.
  • Prefilter / restrict rows at read time — tenancy scoping, row-level security, drop soft-deleted rows.
  • Mask / redact at source, add auth / caching / materialization, or custom snapshotting.
  • Supply in-memory / fixture data for tests.
QuerySolver(ABC)

The execution seam

Turns a TSAL query plus the silver DataFrames into results through a 6-stage filter→solve pipeline. Customize it to:

  • Push down a domain prefilter / pruning the built-in pipeline doesn't.
  • Support a physical layout column-mapping can't express — a different join/pivot to resolve channels.
  • Read a different time-series encoding in solve().
  • Post-process the solve output — redact / round / annotate, or inject business rules.
  • Custom candidate selection or performance strategies.
What does not need a custom implementation: column renames and narrow-vs-wide shape differences are already handled by DefaultSolver + SolverConfig. A custom solver is only for behaviour the config can't express; a custom measurement-DB is only for a different backend / access path — not for renaming columns.

Lifecycle — register → config → query

The solver and the measurement-DB travel the identical path. Importing the package populates a process-global registry; the config only ever carries the registered name; resolution and typed-config validation happen at parse time; the built solver then runs its pipeline over the built measurement-DB.

Bring your own

Write a subclass, decorate it to register under a name, and name it in config. The driver must import my_pkg (which runs the decorator) before the config is parsed.

Register — Python
from impulse_query_engine.analyze.query.solvers import register_solver, SolverConfig
from impulse_query_engine.analyze.query.solvers.default_solver import DefaultSolver

class MyConfig(SolverConfig):
    redact_columns: list[str] = []

@register_solver("MySolver", MyConfig)
class MySolver(DefaultSolver):
    def solve(self, query, channels_df, selections, dtypes):
        df = super().solve(query, channels_df, selections, dtypes)
        ...  # custom behaviour
        return df
Select — report config
{
  "query_engine": {
    "solver": "MySolver",
    "solver_config": { "redact_columns": ["vin"] }
  }
}
Keep the 6-stage QuerySolver(ABC) as the contract. A custom solver typically subclasses DefaultSolver and overrides one stage (e.g. solve() to post-process, or a filter stage to prune). Its typed solver_config subclass survives validation instead of being down-cast to the base.
Register — Python
from pydantic import BaseModel
from impulse_query_engine.measurement_db import (
    AbstractMeasurementDB, register_measurement_db, MeasurementDbBuildContext,
)

class MyBackendConfig(BaseModel):
    endpoint: str
    secret_scope: str

@register_measurement_db("MyBackend", MyBackendConfig)
class MyMeasurementDB(AbstractMeasurementDB):
    @classmethod
    def from_config(cls, ctx: MeasurementDbBuildContext) -> "MyMeasurementDB":
        return cls(ctx.backend_config, ws=ctx.ws)

    def container_metrics(self, spark): ...   # e.g. join several physical tables
    def channel_metrics(self, spark): ...
    def channels(self, spark): ...
    # override the optional reads only if the report uses them
Select — report config
{
  "source":         { "...": "used only by the default Delta/UC backend" },
  "query_engine":   { "solver":  "MySolver",  "solver_config": { "...": "..." } },
  "measurement_db": { "backend": "MyBackend",
                      "config":  { "endpoint": "...", "secret_scope": "..." } }
}
Backward compatible. Omit the measurement_db section and Impulse resolves the default Delta/UC backend and builds it from source, exactly as today. source is never modified — it is the default backend's config block; a custom backend puts its parameters in measurement_db.config, validated through the registered config_cls. Ad-hoc / ML notebooks can skip the registry entirely and construct the instance directly.

Strategy C is applied to both axes — a solver registry and a symmetric measurement-DB registry.

Recommendation & contract

Adopt the name registry for both QuerySolver and MeasurementDB, backed by a new ABC for the DB, unified by one principle: an implementation is selected by registered name in config — never by a class path imported from config data. Direct instance construction (injection) is retained only for code-driven use (ad-hoc / ML notebooks and tests), never as the reporting seam.

The measurement-DB is made config-driven (not injected) because every Report in the codebase is built from config and then constructs its DB internally — no call site passes a prebuilt component, so a Report(db=…) param would be the lone non-config seam and unusable in a pure-config Workflow.

Why an ABC, not a Protocol

The codebase uses ABCs everywhere (Event, Aggregation, Sink, QuerySolver); an ABC gives eager “you forgot method X” errors at instantiation and matches house style. (A Protocol stays a zero-touch alternative if structural typing is ever wanted.)

Field case — reshaping a raw silver layer

A real downstream integration exercised exactly these seams — the strongest evidence for the read-seam design, and a caution about doing it the hard way before the registries existed.

What the integration had to do

  • It forked / vendored Impulse and added a solver name-registry plus overridable load_* table-read hooks to DefaultSolver — the registry recommended here, and precisely the load_* extension point the design deliberately rejected as “too invasive.”
  • On those hooks it layered a DefaultSolver subclass whose loaders reshape raw → silver: a clustering-key prefilter (session / signal / date on the physical columns, so the read prunes files), union a secondary statistics variant, join three reference tables (test → vehicle → fleet) to surface container tags, derive a composite two-part channel_id, map columns inside the loader, and hand a silver-shaped frame to a per-entity transformer. A domain defect-code list (stored as POI values) is folded into a container_metrics array. Every solver stage was inherited unchanged.
  • A typed SolverConfig subclass carried the extra raw-table names and the prefilter keys — the config declares which tables while the class keeps the how.

What it validates: the entire customization is read-seam work — combining several physical tables into one logical silver layer — so it belongs in a MeasurementDB, not the solver. With the measurement-DB port + registry, the same integration would implement an AbstractMeasurementDB whose channels / channel_metrics / container_metrics (+ tags) do the union / join / channel_id / reshape / prefilter, register it by name, and run the stock DefaultSolver unchanged — no fork, no load_* hooks. The load_* overrides map almost one-to-one onto the ABC's read methods; the team's own design review independently favoured a read-seam approach.

Caveat — beyond these seams: DefaultSolver.solve() returns a lazy DataFrame with no teardown hook, so a backend that materializes temporary tables has nowhere to clean them up. That's a solver-lifecycle gap, orthogonal to solver / DB selection, that neither registry addresses.
